  - **Bug real encontrado en el harness de simulación, no en la app**: la primera versión del script fallaba con confusión de identidad entre usuarios simulados (el reporte del setter terminaba atribuido al closer). Causa: el script envolvía TODAS las llamadas HTTP dentro de un único `with app.app_context():` externo — Flask-Login cachea el usuario resuelto en `flask.g`, que vive atado al app context; como Flask reusa el app context ya activo en vez de empujar uno nuevo por request cuando detecta uno igual ya en el stack, el segundo usuario logueado heredaba el `flask.g` del primero. Fix: las llamadas de `test_client()` se sacaron de cualquier `app_context()` manual (cada request de Flask empuja el suyo propio si no hay uno activo); el `app_context()` solo se usa para leer/limpiar la base de datos antes y después. Además se detectó que el usuario de triage por defecto (`Romer`) tiene `is_active=False` en la base local — `UserMixin.is_authenticated` de Flask-Login devuelve `self.is_active`, así que una cuenta desactivada nunca se considera autenticada aunque la sesión tenga su `_user_id` — el script se ajustó para tomar usuarios activos (`Dari` en vez de `Romer`).
